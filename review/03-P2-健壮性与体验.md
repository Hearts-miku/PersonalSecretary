## 🆕 N-21 任务被取消后，进度标志不会复位

**位置**：[WorkLogViewModel.kt:61,157,222,242,259](https://github.com/Hearts-miku/PersonalSecretary/blob/c5a0225/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L61)
**置信度**：高（代码路径确定）／ 触发时序需实机确认

本轮引入的 `activeAiJob` 让四个 AI 入口共用一个任务槽，每个入口都是
「先取消旧任务、再启动新任务」：

```kotlin
activeAiJob?.cancel()
activeAiJob = viewModelScope.launch {
    _isProcessingAI.value = true
    ...
    _isProcessingAI.value = false     // ← 被取消时这行永远不会执行
}
```

协程被取消后会在下一个挂起点抛出 `CancellationException`，**末尾的标志复位随之跳过**。

### 触发路径

1. 用户在主页触发日志总结 → `_isProcessingAI = true`
2. 切到个人中心点「AI 提炼工作经历」→ 总结任务被 `cancel()`，新任务设
   `_isGeneratingWorkExp = true`
3. 总结协程再没机会执行 `_isProcessingAI.value = false`
4. **主页与时间线的进度条永久停留，相关按钮持续禁用**

[`cancelActiveAiJob()`](https://github.com/Hearts-miku/PersonalSecretary/blob/c5a0225/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L66)
会一次性复位全部六个标志，设计是对的——但它只挂在简历页和设置页的两个「取消」按钮上，
覆盖不到上面这条从个人中心触发的路径。

**建议**：把标志复位放在**启动新任务之前**统一执行，而不是依赖被取消的协程自己收尾。
或者给每个入口独立的 Job 槽，避免互相取消。

## 🆕 N-22 取消机制让双写管线可被中途打断

**位置**：[WorkLogRepository.triggerAISummarize](https://github.com/Hearts-miku/PersonalSecretary/blob/c5a0225/app/src/main/java/com/example/data/repository/WorkLogRepository.kt)

`triggerAISummarize` 是四步双写：写 `worklogs/<date>.md` → 写 Room → 覆写职业档案
+ 版本快照 → 按日期清理原始笔记。步骤之间有多个挂起点（数据库写入、AI 调用）。

「双写缺少事务性」是长期记录在 [05-架构观察](05-架构观察.md) 的问题，此前只在**进程被杀**
时才可能触发。引入 `activeAiJob` 的主动取消后，**它变成了用户日常操作就能触及的路径**。

最值得注意的窗口是第 3 步内部：

```kotlin
markdownManager.writeCareerProfile(evalObj.updatedProfileMarkdown)   // 文件已写
// ← 若在此处被取消
profileDao.insertOrUpdateProfile(currentProfile.copy(...))          // 数据库未写
```

此后文件与数据库分叉，且没有任何一致性校验或修复逻辑会发现它。

**建议**：把 Room 侧的多次写入包进 `@Transaction`；对销毁性步骤（清理原始笔记）
确认前序全部成功；或者让 `triggerAISummarize` 在关键区段使用
`withContext(NonCancellable)`。

## P2-20 缺少数据出境告知

用户笔记、职业档案、语义搜索的日志摘要、经历生成的近期日报、导入文件的内容，
都会发往用户自行配置的第三方端点。应用内没有任何隐私说明，而个人中心和简历页挂着
「隐私保护」徽章——该徽章实际只表示简历里用了占位符。

收敛为单一自定义端点后这条更需要说明：应用无从保证对端如何处理数据。
