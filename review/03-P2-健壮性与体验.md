# P2 — 当前缺陷

## N-40 新问题：把推理过程或截断响应当作正式成功结果

位置：[AiRepository.kt:208](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/ai/AiRepository.kt#L208)。content 为空时直接回退 reasoning_content；只要非空即 Result.success。推理过程可能是分析、草稿或尚未完成的计划，不等于最终日报/履历。调用方看到成功就会保存并替换正文，日报还会标记 isSummarized。本机 HTTP 模拟响应已实测确认推理字段被成功返回；自动保存后果由调用链确认。

同一通用入口在 finish_reason=length 时也改为成功并拼接“报告已部分截断”说明，它影响的不只是报告，而是所有 AI 调用。对于日报/经历，半截文本可能替换现有完整内容；说明文字不能替代完整性状态。结构化 JSON 调用则可能继续在解析阶段失败。

建议区分 final/partial/reasoning-only。正文为空应明确失败；不把推理过程写入文档。部分报告若产品希望保留，应独立作为草稿展示，由用户确认，不自动覆盖已有完整版本。验收正文空但 reasoning 非空，以及 length 截断响应，旧文档不被无提示替换。

## N-36 部分修复：清空保护只覆盖总结，普通写入仍可回流

位置：[WorkLogRepository.kt:126](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L126)、[WorkLogRepository.kt:405](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L405)、[WorkLogRepository.kt:614](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L614)、[WorkLogRepository.kt:805](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L805)；[WorkLogViewModel.kt:775](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L775)。

总结现在有 epoch 校验，clearAllData 也使用同一个 mutex；其新增测试已经验证“总结等待期间清空后，不回写旧总结”。但普通保存、经历手动保存、恢复版本等没有代际校验和共享锁，也不都属于 activeAiJob。ViewModel 清空只等这个单一 Job，不阻止新的写入入口。

addRawNote 自身也是先写文件、后取锁写数据库：若它在清空已持锁但尚未删除文件时追加，随后文件被清空，解锁后它仍会写回数据库，因为没有起始代际检查。结果是清空后记录回流且文件副本缺失。此处是静态可达时序，非已完成真机复现。

建议所有写入口使用统一重置代际与提交边界，清空期间禁止新写入；文件和数据库阶段一并协调。验收暂停普通提交/手动保存于写入中间，再清空，确认结束后两处均空。

## N-35 部分修复：isActive 不代表尚未完成，显式取消会丢失等待链

位置：[WorkLogViewModel.kt:78](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L78)、[WorkLogViewModel.kt:132](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L132)、[WorkLogViewModel.kt:781](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L781)。

launchExclusiveJob 只有 previousJob.isActive 时才 cancelAndJoin。取消中的任务可 isActive=false 但尚未完成，尤其仍处于 NonCancellable 写区。显式取消又先把 activeAiJob=null，再启动另一个协程等待，后续新任务拿不到旧 Job。快速 A→B→C 替换时，B 等待 A 可被 C 取消，C 等完 B 不保证 A 完成。

此外 finally 无 token 检查地调用 statusSetter(false)，旧任务晚退出仍可能把新任务的相同 busy 状态清掉。token 目前只在启动/异常处检查，不能保护所有提交和收尾。

建议保留可等待的任务链，按 isCompleted/无条件 join 判断完成，序列化任务切换，并按身份更新状态。静态分析；需要用可控取消中的 Job 验证，不把现有 Repository 测试算作 ViewModel 生命周期测试。

## N-32 部分修复：保留历史后，截取 rawNotes 开头会漏掉真正补录

位置：[WorkLogRepository.kt:343](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L343)、[WorkLogRepository.kt:354](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L354)、[WorkLogRepository.kt:391](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L391)。

rawNotes 现在是完整历史，不是“补录待整理记录”。报告仍取 rawNotes.take(rawBudget)，新增 B 追加在末尾，因此旧记录超过预算时，B 会完全不进入报告；2:1 分配并未解决新旧事实识别。摘要短时未用完的预算也不会转给原文。

覆盖提示现在确实存在，但只加入模型输入，最终输出/UI 没有确定性保留：generateReport 直接返回模型正文。模型不复述提示时用户仍不知道缺哪些日期。超过 20 天时 800 字下限和额外标题还会使后面的日期被 break 排除。

补充 Repository 探针已确认：6000 字历史之后补录唯一标记，实际交给假 AI 的 prompt 不含该标记。建议单独追踪未总结增量，优先完整纳入；覆盖日期/截断状态由程序绑定报告并展示，不依赖模型复述。验收长历史后追加唯一新事实 B，捕获真实 prompt 检查 B，并让假模型不复述覆盖提示检查 UI 元数据。

## N-37 剩余问题：历史文本计数不能标识临时笔记，多行条目无法清理

位置：[MarkdownFileManager.kt:160](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/markdown/MarkdownFileManager.kt#L160)、[MarkdownFileManager.kt:181](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/markdown/MarkdownFileManager.kt#L181)；[WorkLogRepository.kt:301](https://github.com/Hearts-miku/PersonalSecretary/blob/2fe3642f86a78f6bc32a12e2ae1bfc8c705c147e/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L301)。

第一轮 A 已总结、临时 A 已删，但 Room 仍保留 A。第二轮捕获历史 A+B 后，等待期间用户又追加 A；按快照 A+B 清理时，会用“历史 A 的计数”删除本轮新增 A。当前频次消费只能保护同一批的重复，不能识别已被清理的旧批次。

多行条目也不匹配：targetsToRemove 拆成单行，而 normalizedBlock 用换行重新合成整块。一条两行笔记总结后会永久留在临时文件。更糟的是，单行新增文本可能消耗属于旧多行条目的那一行计数。

上述跨批次同文误删、多行条目残留均已调用生产文件管理类复现（详见 07）。建议给每次追加稳定 ID，捕获当前待处理 ID，而不是把完整历史原文重解释成删除列表；保留原始多行条目边界。Room 原文现已保留，因此不再称为上轮同等级的完整事实丢失。
