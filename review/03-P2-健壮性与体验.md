## 🆕 N-23 连接测试与实际请求走的不是同一个 URL

**位置**：[AiRepository.kt:113](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/data/ai/AiRepository.kt#L113)（测试路径）、
[:34](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/data/ai/AiRepository.kt#L34)（实际路径）、
[:138](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/data/ai/AiRepository.kt#L138)（端点拼接）
**置信度**：高（代码路径确定）／ 是否失败取决于服务端

两条路径对同一个 Base URL 的规范化不同：

```kotlin
// testConnection：以 chat/completions 结尾时原样保留
val normalizedUrl = if (trimmedUrl.endsWith("/") || trimmedUrl.endsWith("chat/completions") || ...) trimmedUrl else "$trimmedUrl/"

// 实际请求 getEffectiveBaseUrl：一律补尾斜杠
return if (url.endsWith("/")) url else "$url/"
```

用户填 `https://x/v1/chat/completions` 时：

| 路径 | 最终端点 |
|---|---|
| 连接测试 | `https://x/v1/chat/completions` |
| 实际请求 | `https://x/v1/chat/completions/` |

**测试显示成功，而真实调用在对尾斜杠敏感的服务端返回 404 / 405。** 连接测试的意义
正在于代表真实请求，两者分叉会直接误导用户。

**附带**：两条路径都接受 `http://`（测试路径还显式放行），但 targetSdk 36 默认禁止明文流量，
manifest 也未声明 `usesCleartextTraffic`。填 `http://` 能通过校验，发请求时却抛
"CLEARTEXT communication not permitted"。建议要么在校验阶段直接拒绝并说明原因，要么明确支持。

**建议**：抽出一个 `normalizeEndpoint(baseUrl)`，测试与实际请求共用；为它补一条测试，
覆盖「带 / 不带尾斜杠」「以 chat/completions 结尾」三种输入。

## 🆕 N-24 重新总结会把旧 AI 总结写进 `rawNotes`

**位置**：[WorkLogRepository.kt:148-180](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L148)
**置信度**：高

本轮 `triggerAISummarize` 增加了回退：`rawNotes` 为空时改用 `summaryMarkdown` 作为输入。
这个回退本身合理——从 markdown 恢复的日志 `rawNotes` 就是空的，否则无法重新总结。

问题在写回：

```kotlin
logDao.insertOrUpdate(
    DailyWorkLogEntity(
        ...
        rawNotes = rawContent,          // ← 此时 rawContent 是旧的 AI 总结
        summaryMarkdown = summaryMarkdown,
        ...
    )
)
```

后果：

1. 时间线里「查看原始笔记」显示的其实是上一轮 AI 文本
2. 下次重新总结时 `rawNotes` 已非空，**上一轮 AI 输出被当作 `<user_raw_content>` 送回模型**，
   形成「总结的总结」，内容逐轮漂移
3. 护栏 prompt 的「严禁臆造用户没有提及的工作内容」以「用户原文」为锚点，这条锚点被悄悄替换了

**建议**：输入来自 `summaryMarkdown` 时，写回 Room 保持 `rawNotes` 原值（空）不变。

## 🆕 N-26 批量整理的空分支会让任务脱离 `activeAiJob`

**位置**：[WorkLogViewModel.kt:185-191](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L185)
**置信度**：中（依赖调度器语义，需实机确认）

```kotlin
fun triggerAISummarizeAllUnsummarized() {
    activeAiJob?.cancel()
    activeAiJob = viewModelScope.launch {            // ② 外层赋值最后才发生
        val unsummarizedLogs = allLogs.value.filter { ... }
        if (unsummarizedLogs.isEmpty()) {
            triggerAISummarizeSelectedDate()         // ① 内部又执行 activeAiJob = launch { ... }
            return@launch
        }
        ...
```

`viewModelScope` 使用 `Dispatchers.Main.immediate`：在主线程发起时，协程体会同步执行到第一个
挂起点才返回。空分支里没有挂起点，于是顺序是：内层把 `activeAiJob` 指向真正在跑的总结任务 →
外层协程体结束 → `launch` 返回 → 外层赋值把 `activeAiJob` 覆盖为已结束的外层 Job。

**结果：真正在跑的总结任务成了孤儿，「取消」按钮停不下它。**

**建议**：空分支直接内联执行单日期总结，不要调用会重新赋值 `activeAiJob` 的函数。

## 🆕 N-27 批量整理会改写「记录日期」

**位置**：[WorkLogViewModel.kt:205](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L205)、
[:141](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L141)

批量循环逐个执行 `_selectedDate.value = date`，结束时停在最后处理的日期（按排序通常是最旧的那天）。
而本轮 `submitRawInput` 改为按 `_selectedDate` 归档——整理完再去 Home 写笔记，会记到那个旧日期。

Home 页的「记录日期」与提交按钮文案会显示目标日期，用户看得到，因此归为小问题。
建议批量整理结束后恢复发起前的日期。

## N-21 任务被取消后，进度标志不会复位（上轮遗留，已被放大）

**位置**：[WorkLogViewModel.kt:165-205](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L165)

被取消的协程不会执行到末尾的 `_isProcessingAI.value = false`。`cancelActiveAiJob()`
（[:66](https://github.com/Hearts-miku/PersonalSecretary/blob/e543020/app/src/main/java/com/example/ui/viewmodel/WorkLogViewModel.kt#L66)）
会复位全部标志，但只挂在简历页与设置页的取消按钮上。

**本轮批量整理放大了它**：循环里依次跑多条管线，没有 `try/finally`，可被打断的窗口从一条管线
变成 N 条。

**建议**：标志复位放进 `finally`，或在启动新任务前统一复位。

同源小问题：`cancelActiveAiJob()` 会复位 `_isTestingConnection`，但连接测试的协程并不在
`activeAiJob` 里，不会被真正取消——防重复触发的守卫提前解除，可以并发发起第二次测试。
