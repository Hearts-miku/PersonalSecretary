# 架构观察

跨文件的结构性问题，不是逐条 bug。

---

## 1. 双写存储已经完整

| 文件 | 写 | 读 |
|---|---|---|
| `temp/raw_notes.md` | `appendRawNote` | 无（Room 的 `rawNotes` 是真数据源） |
| `user/career_profile.md` | AI 评估 / 手动编辑 / 导入 | 所有下游 AI 调用 + 恢复逻辑 |
| `worklogs/YYYY-MM-DD.md` | `triggerAISummarize` | `restoreLogsFromMarkdownIfNeeded` |
| `user/work_experiences.md` | 生成 / 导入 / 手动编辑 / 版本恢复 | 恢复逻辑 |
| `user/project_experiences.md` | 同上 | 恢复逻辑 |
| `user/generated_resume.md` | `saveResume` | `getSavedResume` |

首轮报告里「日报只写不读」「工作/项目经历只存在于 Room」这两处不对称都已消除。
markdown 层现在是真正的持久化底座，Room 可以从它完整重建——这也是 P0-6 得以从
`fallbackToDestructiveMigration` 切换到真实迁移的前提。

**遗留**：`todo_items` 与 `experience_versions` 仍然只在 Room 里，没有磁盘副本。
版本快照尤其值得留意——它是用户找回被覆盖内容的最后一道防线，[N-8](03-P2-健壮性与体验.md)
（编辑无法取消）出现时更是如此。

## 2. 提示词隔离约定出现了第一处破口

项目的三层设计——输入消毒 → `<user_raw_content>` 标签隔离 → 系统护栏提示词——在
前几轮已经稳定：消毒收缩到只做标签转义 + 长度截断，不再破坏用户内容。

本轮新增的 `refineImportedContent` **发明了一个新标签 `<imported_data>`，而 sanitizer
并不认识它**（详见 [N-6](02-P1-功能与安全.md)）。

这类破口的代价不在单次风险，而在于**约定一旦有例外，后续代码就失去了"照着抄"的
可靠样板**。项目里现在有 8 个 AI 功能，7 个遵循约定、1 个不遵循——下一个新功能的
作者按哪个抄，是掷硬币。

隐私占位符常量的归属问题上一轮已经解决（统一到
[`AISafetyManager.PRIVACY_PLACEHOLDERS`](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/ai/AISafetyManager.kt#L23)），
标签约定也应该同样收口——比如让 `sanitizeUserInput` 接受标签名参数，由它负责转义
对应的闭合标签。

## 3. 仓库层的调度器约定已恢复零例外

第 3 轮出现的破口（`getSavedResume` / `saveResume` 是普通函数）已在第 4 轮修正为
`suspend` + `withContext(Dispatchers.IO)`。本轮新增的
`updateWorkExperiencesManually` / `updateProjectExperiencesManually` / `clearAllData` /
`exportDataToZip` 全部遵循该约定。

UI 层仍有一处主线程 IO：[P2-3](03-P2-健壮性与体验.md) 的
`remember { markdownManager.getMarkdownDirectoryInfo() }` 直接绕过了 Repository。

## 4. 「失败被包装成成功」是反复出现的模式

这已经是第三次以不同形式出现：

| 编号 | 表现 |
|---|---|
| P2-2 | JSON 解析失败 → 播报「工作履历评估完毕（无须大幅调整）」 |
| P2-9 | 语义搜索 AI 调用失败 → 显示「未找到匹配的历史工作日志」 |
| [N-7](03-P2-健壮性与体验.md) 🆕 | AI 提炼失败 → 播报「已由 AI 提炼并导入！」，实际存的是原文 |

三处的共同结构是 `result.getOrNull() ?: fallback` 之后走同一条成功分支，把降级和成功
混为一谈。

**这不是三个独立的 bug，是一个缺失的约定**：AI 调用失败后若选择降级，必须让用户知道
发生了降级。建议统一一种表达（例如 snackbar 前缀「⚠️ AI 未能处理，已按原文导入」），
新功能照此办理。

---

## 5. 错误处理仍是全局静默降级

全项目只有一处 `Log` 调用，位于零调用的 `AutoSummaryScheduler` 中。三个 JSON 解析函数、
`triggerAISummarize` 的步骤 2/3、`MarkdownFileManager` 的全部 File IO 都没有日志。

本轮新增的 `clearAllData` 与导入流程有 try/catch 并 snackbar 提示，方向是对的。

---

## 6. 测试覆盖与改动速度不匹配

当前唯一的测试是
[`AISafetyManagerTest`](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/test/java/com/example/AISafetyManagerTest.kt)（3 条用例）。

而这五轮里已经发生过**两次回归**：第 2 轮回退了 8 项修复，第 4 轮回退了 P1-13。两次
都是在没有任何断言拦截的情况下进入 main 的。

改动速度不慢——本轮就新增了三个功能。但验证手段停留在人工审计上，而人工审计是
滞后的（问题进 main 之后才发现）。这是当前最需要补的结构性缺口。

---

## 7. 分层依然干净

`Composable → ViewModel → Repository → {Room, Markdown, AI}` 无反向依赖；`Result<T>` 在
AI 边界使用一致；三个编辑态都走 ViewModel（与 P1-14 验证过的模式一致）；`testTag`
覆盖主要交互控件，本轮新增的 `clear_all_data_btn` 也遵循了命名约定。

修复应在现有结构内进行，不需要重构。
