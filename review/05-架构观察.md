# 架构观察

跨文件的结构性问题，不是逐条 bug。

---

## 1. 双写缺少事务性 —— 本轮从「理论问题」变成「可触及问题」

这是首轮审计就记录的结构性问题：`triggerAISummarize` 的四步双写之间没有原子性保障。
过去几轮已经拆掉了破坏性最强的组合（空总结校验、按日期清理、覆写前快照），
但**根本的非事务性一直存在**。

此前它只在进程被杀时才可能触发，属于低频意外。本轮引入 `activeAiJob` 的主动取消后
（见 [N-22](03-P2-健壮性与体验.md)），**用户在界面上的日常切换就能打断管线**——
风险等级实质上升了。

这类「新功能让一个既有的结构性弱点变得可达」的情况值得单独记录：问题本身不是新的，
但它的暴露面变了。

**建议的收口方向**：Room 侧多次写入包进 `@Transaction`；文件写入与数据库写入之间的
关键区段用 `withContext(NonCancellable)`；销毁性步骤（清理原始笔记）确认前序全部成功。

---

## 2. 加解密的层次归属已收口

`AiRepository.getEffectiveApiKey` 不再解密，边界现在清晰：
**出了 `WorkLogRepository` 就是明文，进了 DAO 就是密文**，其余层不关心。

异常路径的取向也改对了——解密失败返回空字符串（走已有的「未配置 API Key」提示），
而不是把密文当明文发出；降级为 Base64 时记录日志。对凭据这类数据，
「明确失败」确实比「静默降级」合适。

`base64Encode` / `base64Decode` 优先 `java.util.Base64`、失败回落 `android.util.Base64`
的写法，除了兼容性还有个副产品：**让加解密逻辑可以在纯 JVM 单测里被验证**。
这是本轮测试得以落地的直接原因。

## 3. 双写存储的恢复覆盖

| 数据 | 磁盘副本 | 破坏性迁移后可恢复 |
|---|---|---|
| 日报 / 职业档案 / 工作经历 / 项目经历 / 简历 | ✅ | ✅ |
| **待办** | 无 | ❌ |
| **经历版本快照** | 无 | ❌ |

前五类恢复链完整。版本快照仍是缺口——它是用户找回被覆盖内容的最后一道防线，
而数据库当前处于破坏性回落状态。

## 4. 提示词隔离约定：零例外

`sanitizeUserInput` 的 `tagName` 参数 + 全部调用点包标签，自上一轮起保持零例外。

## 5. 「失败被包装成成功」已收口，解析层还差两处

P2-2、P2-9、N-7 三处已统一用 `⚠️` 前缀表达降级。`parseCareerUpdateFromJson` 改用
`mapCatching` 让失败向上传播。剩 `parseTodosFromJson` 与 `parseSearchResultsFromJson`
仍静默返回空结果。

## 6. 测试：从「有一个」到「有覆盖」

| 文件 | 用例 | 覆盖 |
|---|---|---|
| `AISafetyManagerTest` | 3 | 长度截断、标签转义、代码块保真 |
| `CryptoManagerTest` 🆕 | 6 | 往返、`v1:` 兼容、明文兼容、两种损坏输入的 fail-safe |
| `AiRepositoryValidationTest` 🆕 | 4 | 三项配置缺失时各自提前失败 |

这三个文件精确对应了审计中最需要锁定的行为：P1-7（曾被回退一次）、P1-4 / N-19
（新建的加密机制）、P1-17（曾是发布阻断项）。

**仍未覆盖**：`CryptoManager` 的 `v2:` 加密路径在 JVM 环境不可达（Keystore 不可用，
代码注释已说明），需要 instrumented test；`extractJsonSubstring` 的边界用例
（曾在回归事件 1 中丢失过）也还没有断言。

---

## 7. 分层依然干净

`Composable → ViewModel → Repository → {Room, Markdown, AI}` 无反向依赖；
`Result<T>` 在 AI 边界使用一致；仓库层调度器约定零例外；加解密边界已收口。

唯一的新增复杂度是共享的 `activeAiJob` 任务槽——四个 AI 入口共用一个 Job，
互相取消（见 [N-21](03-P2-健壮性与体验.md)）。若要保留可打断能力，
给每个入口独立的 Job 槽会更符合当前的分层清晰度。
