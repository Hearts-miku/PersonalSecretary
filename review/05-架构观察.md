# 架构观察

跨文件的结构性问题，不是逐条 bug。

---

## 1. AI 层收敛完成

D-1 执行完毕：`GeminiRepository` 更名为 `AiRepository`，只保留一条 OpenAI 兼容路径，
secrets 插件与 `BuildConfig` 依赖一并移除。

**执行时的挑拣是准确的**——三家 provider 的截断检测原本是同一批工作的产物，删除时
正确保留了 OpenAI 的 `finish_reason` 检测与 o1/o3 的 `temperature` 保护，没有连带
删掉仍然有用的部分。这类「删一半留一半」的清理最容易出错，本轮做对了。

配置解析现在是三条平行的空值检查（`baseUrl` / `apiKey` / `model`），各自给出可读的
失败原因，比原先的 provider 分支树清晰得多。

---

## 2. 加解密的层次归属需要收口

本轮引入了真加密（Keystore + AES-256-GCM），设计上的向下兼容做得很好：
`v2:` → `v1:` → 无前缀明文，三层依次回落。

但**编解码的责任分散在两层**（见 [N-20](03-P2-健壮性与体验.md)）：
`WorkLogRepository` 解密一次，`AiRepository` 又解一次。功能上无害，代价是读代码时
无法判断某个 `UserSettingsEntity.apiKey` 手里是密文还是明文。

建议明确一条边界：**出了 `WorkLogRepository` 就是明文，进了 DAO 就是密文**，
其余层不再关心。

另一处值得注意的是异常路径的取向（[N-19](03-P2-健壮性与体验.md)）：当前两条失败路径
都选择「继续可用」——加密失败降级为 Base64、解密失败返回密文。对凭据这类数据，
「明确失败」通常比「静默降级」更合适。

## 3. 双写存储

| 数据 | 磁盘副本 | 破坏性迁移后可恢复 |
|---|---|---|
| 日报 | `worklogs/*.md` | ✅ |
| 职业档案 | `career_profile.md` | ✅ |
| 工作/项目经历 | `work_experiences.md` / `project_experiences.md` | ✅ |
| 简历 | `generated_resume.md` | ✅ |
| **待办** | 无 | ❌ |
| **经历版本快照** | 无 | ❌ |

前四类的恢复链已经完整。剩下两类中，**版本快照尤其值得补**——它是用户找回被覆盖内容
的最后一道防线，而当前数据库正处于破坏性迁移状态（见 [P0-6 回归](02-P1-功能与安全.md)）。

## 4. 提示词隔离约定：零例外

`sanitizeUserInput` 的 `tagName` 参数 + 全部调用点包标签，本轮随
[P1-16](07-已修复与回归记录.md) 的修复达成零例外。语义搜索现在也对查询词和每条日志
预览分别消毒，并加了 18000 字预算——采用的是累加式收集，不是早期 `takeWhile` 那种
「遇到第一条超预算就整体停止」的写法。

---

## 5. 「失败被包装成成功」已收口，解析层还差两处

P2-2、P2-9、N-7 三处已统一用 `⚠️` 前缀表达降级。`parseCareerUpdateFromJson` 改用
`mapCatching` 让失败向上传播，方向正确。

剩 `parseTodosFromJson` 与 `parseSearchResultsFromJson` 仍在 catch 里静默返回空结果，
建议推广同样的做法。

## 7. 分层依然干净

`Composable → ViewModel → Repository → {Room, Markdown, AI}` 无反向依赖；`Result<T>`
在 AI 边界使用一致；编辑态走 ViewModel；仓库层调度器约定零例外；`testTag` 覆盖主要
交互控件（本轮新增的 `export_data_zip_btn` 也遵循了命名约定）。

唯一的层次模糊是加解密归属（见第 2 节）。修复应在现有结构内进行。
