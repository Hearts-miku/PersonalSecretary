## 二、回归事件记录

这五轮里发生过**两次回归**，都在没有断言拦截的情况下进入了 main。

### 事件 1：第 2 轮回退 8 项（`b4735eb`）— 已恢复

`9987fc9` 修复的 8 项被整体回退，其中 4 项与凭据安全直接相关。第 3 轮（`884ed39`）
全部恢复，且是按项挑拣而非整文件回滚。

**成因**：当时 `GeminiRepository.kt` 相对首轮基线的净差异仅剩 +6/−2 行，
`AISafetyManager.kt` 除新增部分外与基线完全一致——典型的**基于陈旧文件副本编辑后
整体覆盖**。佐证是同一次提交里 Gemini 的 `finishReason` 被扩充（正是当轮报告的建议），
而同文件其他两家的同类检测却回到了原始状态。

### 事件 2：第 4 轮 P1-13 回归（`f02ac83`）— 至今未恢复

第 3 轮用 `remember(settings.id)` 修好了 P1-13，但引入了首次组合竞态（N-2）。
第 4 轮为修 N-2 加了 null 守卫，同时把 key 改回 `remember(settings)`——N-2 解决了，
P1-13 回来了。

**成因**：两个约束（等待加载完成 / 不跟随后续变化）被当成互斥的，实际可以同时满足。
详见 [02-P1-功能与安全.md](02-P1-功能与安全.md)。

### 规避方式

1. 改动前先 `git fetch && git rebase origin/main`
2. 提交后自查 `git diff <上一次修复提交> HEAD -- <改动文件>`，确认没有意外删除
3. **补测试**——这是唯一能自动拦截此类问题的手段
