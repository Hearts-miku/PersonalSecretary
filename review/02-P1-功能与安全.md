## N-39 新回归：清空原始笔记后，补录再总结覆盖已有全天成果

位置：[WorkLogRepository.kt:185](https://github.com/Hearts-miku/PersonalSecretary/blob/48d8b8f059717f9fe6b730662e8e35068df9db63/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L185)、[WorkLogRepository.kt:148](https://github.com/Hearts-miku/PersonalSecretary/blob/48d8b8f059717f9fe6b730662e8e35068df9db63/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L148)、[WorkLogRepository.kt:178](https://github.com/Hearts-miku/PersonalSecretary/blob/48d8b8f059717f9fe6b730662e8e35068df9db63/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L178)。证据：静态完整调用链；未以真实模型端到端复现。

本轮将正常总结后的 rawNotes 从保留原文改为空字符串（192、198 行）。已有 summaryMarkdown 并不会在下次存在 rawNotes 时合并进入输入，148–154 行优先只取新 rawNotes。

可达流程：

1. 记录 A，成功总结为 S(A)。数据库 rawNotes 被清空，临时 A 随后删除。
2. 同日补录 B：addRawNote 保存 rawNotes=B，同时保留 S(A)。
3. 再次总结只把 B 发给 summarizeDailyNotes；该方法不读取旧日报。
4. writeDailySummary 和 insertOrUpdate 用 S(B) 覆盖 S(A)，待办替换也只基于 B。A 不再有完整原始记录或日报可查。

这不依赖并发。首次总结同时就删除原始事实，若原文超过 sanitizer 的 30000 字截断上限，未送入模型的尾部也会被清掉；因此不能把 AI 摘要当作可替代原文的无损存储。

建议：区分不可变原始记录与“待处理游标”，总结成功只推进已处理状态；重建日报时输入完整当天事实，或明确合并旧摘要与增量。保留可恢复版本；不要用原文清空来实现并发修复。

验收：A→总结→补录 B→再次总结，日报包含 A+B，原始事实可查，A 的未完成待办不因 B 的总结消失；超长输入未处理部分仍保持待处理。

建议：原始笔记使用独立 ID 和处理批次；只删除/标记被捕获的 ID。用数据库事务/CAS 或统一写入协调器保护提交；共享 Markdown 文件也必须串行化，不能只按日期加锁。
