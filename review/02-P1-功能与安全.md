## P1-4 `CryptoManager` 是 Base64 编码，不是加密

**位置**：[CryptoManager.kt](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/local/CryptoManager.kt)
**状态**：本轮"实现"了，但未真正解决
**置信度**：高

```kotlin
object CryptoManager {
    fun encrypt(plainText: String): String {
        if (plainText.isEmpty()) return ""
        return Base64.encodeToString(plainText.toByteArray(), Base64.DEFAULT)
    }
    fun decrypt(encryptedText: String): String { ... Base64.decode ... }
}
```

**Base64 是编码，不是加密。** 它不提供任何机密性——拿到数据库文件的人一步就能还原出
API Key。首轮 P1-4 的诉求（防止本地取证/root 场景下的凭据泄露）完全没有被满足。

比"没做"更麻烦的是：类名 `CryptoManager` 和方法名 `encrypt` / `decrypt` 会让后续维护者
（以及下一轮的审计）**误以为凭据已经加密**，从而不再复查这条路径。

**建议**：改用 `EncryptedSharedPreferences`，或 Android Keystore + AES/GCM。若短期内不打算
做真加密，至少把类名和方法名改成 `encode` / `decode` 并加注释说明它不提供机密性——
名实相符比假装安全更重要。

## 🆕 N-5 升级会静默损坏存量用户的 API Key

**位置**：[WorkLogRepository.kt:33,44,48](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L33)
**置信度**：中高（触发与否取决于具体 key，需实机验证）

存量用户库里的 `apiKey` 是**明文**。升级后所有读取路径都会对它调用 `decrypt()`：

```kotlin
val settingsFlow = settingsDao.getSettingsFlow().map {
    it?.copy(apiKey = CryptoManager.decrypt(it.apiKey))     // ← 明文也会被"解密"
}
```

`decrypt` 的两条分支：

| 输入 | 结果 |
|---|---|
| 明文**不是**合法 Base64 | 抛异常 → `catch` 返回原文 ✅ |
| 明文**恰好是**合法 Base64 | 解码成二进制垃圾 → 返回乱码 ❌ |

API Key 基本由 `[A-Za-z0-9_-]` 构成，正好落在 Base64 字符集内。以 Gemini key
`AIzaSy…`（39 字符，`39 % 4 == 3` 是合法余数）为例，大概率解码"成功"并变成乱码。

**后果**：老用户升级后，所有 AI 请求带着乱码 key 返回 401，而设置页显示的也是乱码，
用户无从判断发生了什么。

**根因**：没有任何标记区分「已编码」与「明文」。

**建议**：加版本前缀（存 `v1:<base64>`，读取时只对带前缀的解码），或写一次性迁移把
存量明文转换过去。与 P1-4 的真加密改造一并做最省事。

## 🆕 N-6 `refineImportedContent` 绕开了项目的提示词隔离约定

**位置**：[GeminiRepository.kt:575-604](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/ai/GeminiRepository.kt#L575)
**置信度**：高

```kotlin
val cleanContent = AISafetyManager.sanitizeUserInput(rawContent)
val prompt = """
    ...
    <imported_data>
    $cleanContent
    </imported_data>
    ...
"""
```

[`sanitizeUserInput`](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/ai/AISafetyManager.kt#L12)
只转义 `<user_raw_content>` / `</user_raw_content>` 这一对标签，**完全不认识
`<imported_data>`**。

导入的文件内容里只要出现 `</imported_data>`，后续文字就会跳出数据边界，被模型当作
指令处理。而**导入文件恰恰是这个应用里最典型的不可信输入来源**——用户可能导入从任何
地方拿到的简历模板或文档。

这是项目里第一处偏离自身约定的 AI 调用。`CLAUDE.md` 明确记载：用户输入必须经
`sanitizeUserInput` 且嵌在 `<user_raw_content>` 标签内。

**建议**：改用 `<user_raw_content>` 标签（最简单，且与其余 7 个 AI 功能一致）。若确实
需要区分语义，则让 `sanitizeUserInput` 接受标签名参数并转义对应的闭合标签。

## 🆕 P1-15 Room 迁移从未被执行验证，且已无兜底

**位置**：[AppDatabase.kt:28-58](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/local/AppDatabase.kt#L28)
**置信度**：高（风险确实存在）／ 迁移本身经静态比对**未发现缺陷**

第 4 轮移除了 `fallbackToDestructiveMigration`，换成手写的 `MIGRATION_5_6`——三张表
（`todo_items`、`user_career_profile`、`user_settings`）走「建新表 → 拷数据 → 删旧表 → 改名」
的完整重建。

**静态检查结论**：三条 `CREATE TABLE` 语句已与
[新实体定义](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/local/Entities.kt)逐列比对，
列名、类型、非空、主键声明全部一致，未发现缺陷。

**风险不在代码，在于流程**：

1. `app/schemas/` 下**只有 `5.json`，没有 `6.json`**。`exportSchema = true` 且
   `room.schemaLocation` 已配置，构建时本应生成——文件缺失说明**这几轮改动都没有构建过**
2. 移除 fallback 后，schema 校验不通过不再是「静默清库」，而是启动时抛
   `IllegalStateException` **硬崩溃**，用户只能卸载重装
3. 迁移只覆盖 5→6。低于 5 的库没有路径（此前是 destructive，存量库应该都在 5，可接受）

**建议**：这是下一轮的第一件事——构建一次（生成并提交 `6.json`），并在一个真实的 v5
数据库上跑一遍升级。成本很低，但它是目前唯一一个「错了就全体用户崩溃」的点。

## P1-6 日报注入缺少体积预算

**位置**：[WorkLogRepository.kt:238-239,275-276](https://github.com/Hearts-miku/PersonalSecretary/blob/fa9c62c/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L238)
**状态**：主体已修复，遗留次要问题

```kotlin
val recentLogs = logDao.getAllLogsOnce().take(30).joinToString("\n\n") { "### ${it.date}\n${it.summaryMarkdown}" }
```

`take(30)` 是**条数**限制而非体积限制，靠 `sanitizeUserInput` 的 30000 字截断兜底——那是
粗暴截尾，会把最旧的日志连同职业档案的尾部一起砍掉，用户无感知。空 `summaryMarkdown`
的记录也会被拼成空段落。两处代码完全重复。

因三家 provider 的截断检测都已到位，超限现在会明确失败而非静默产出残缺内容，风险已降低。

**建议**：提取为私有方法，改按累计字符数截断并过滤空记录。
