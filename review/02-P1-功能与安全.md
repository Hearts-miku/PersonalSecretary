## 🆕 P1-17 占位域名成为功能性默认值，用户 API Key 会发往不受控域名

**位置**：[GeminiRepository.kt:49-55](https://github.com/Hearts-miku/PersonalSecretary/blob/7679b62/app/src/main/java/com/example/data/ai/GeminiRepository.kt#L49)、
[Entities.kt:40](https://github.com/Hearts-miku/PersonalSecretary/blob/7679b62/app/src/main/java/com/example/data/local/Entities.kt#L40)
**置信度**：高
**发布阻断**

```kotlin
// GeminiRepository.getEffectiveBaseUrl
return when (provider) {
    "OPENAI"    -> "https://api.your-provider.com/v1/"
    "ANTHROPIC" -> "https://api.your-provider.com/v1/"
    "CUSTOM"    -> "https://api.your-provider.com/v1/"
    else        -> "https://generativelanguage.googleapis.com/"
}
```

```kotlin
// UserSettingsEntity 默认值
val baseUrl: String = "https://api.your-provider.com/v1/",
val selectedModel: String = "my-custom-model",
val apiProvider: String = "CUSTOM"
```

`api.your-provider.com` 是占位符，**不属于本项目**。但它现在是一条完整可执行的默认路径：

1. 新用户安装 → `getSettings()` 创建默认行 → `baseUrl` = 该占位域名
2. 用户在设置页填入自己的 API Key 并保存（Base URL 输入框有默认值，很容易被忽略）
3. 首次触发任意 AI 功能 → `callOpenAiApi` 发出
   `Authorization: Bearer <用户的 key>` 到 `api.your-provider.com`

只要有人注册这个域名并架一个接收端，就能收到用户的 API Key。这不是误操作路径，
**是默认路径**。

**建议**：

- `baseUrl` 默认值改为空字符串
- `getEffectiveBaseUrl` 在 URL 为空时返回失败（或让 `generateContent` 提前返回
  「请先在设置中填写 Base URL」，与现有的「未配置 API Key」提示同构）
- 设置页保存时校验 URL 非空且以 `http(s)://` 开头
- 输入框用 `placeholder` 而非默认值来展示格式示例——占位提示不会被当作真实配置提交

顺带：`selectedModel` 的默认值 `"my-custom-model"` 同理，它会被原样发进请求体。

## P1-4 `CryptoManager` 仍是 Base64，不提供机密性

**位置**：[CryptoManager.kt](https://github.com/Hearts-miku/PersonalSecretary/blob/7679b62/app/src/main/java/com/example/data/local/CryptoManager.kt)
**状态**：名实已相符，真加密未做

第 7 轮的改动方向正确——方法改名为 `encode` / `decode`、注释声明不提供机密性、
`v1:` 前缀解决了存量数据兼容。**名实相符了**，不会再误导后续维护者。

但首轮 P1-4 的原始诉求仍未满足：防止本地取证 / root 场景下的凭据泄露。Base64 是编码，
拿到数据库文件即可一步还原 API Key。

**建议**：改用 `EncryptedSharedPreferences`，或 Android Keystore + AES/GCM。
现有的 `v1:` 前缀机制正好可以复用——真加密时改用 `v2:`，两种格式可以共存。

**附带风险**：`apiKeyText` 用
[`rememberSaveable`](https://github.com/Hearts-miku/PersonalSecretary/blob/7679b62/app/src/main/java/com/example/ui/screens/SettingsScreen.kt#L47)
保存，saved instance state 的 Bundle 在进程死亡时可能落盘，明文 Key 多一个暴露面。
考虑只对非敏感字段用 saveable。

## P1-16 语义搜索把用户数据裸拼进 prompt

**位置**：[GeminiRepository.kt:526-542](https://github.com/Hearts-miku/PersonalSecretary/blob/7679b62/app/src/main/java/com/example/data/ai/GeminiRepository.kt#L526)
**置信度**：高（写法确定）／ 风险等级：中低

```kotlin
val logsPrepared = logs.filter { ... }.take(60)
    .map { log -> "【日期: ${log.date}】: $preview" }   // 未 sanitize、未包标签
    .joinToString("\n\n")

val cleanQuery = AISafetyManager.sanitizeUserInput(query)

val prompt = """
    【搜索查询词/意图】: "$cleanQuery"      // 只加了引号，未包标签
    【候选工作记录列表】:
    $logsPrepared                           // 裸拼
"""
```

八个 AI 功能里，这是**唯一一个把用户数据裸拼进 prompt 的**。`cleanQuery` 虽然过了消毒，
但因为不在标签内，转义 `<user_raw_content>` 对它没有意义。

风险不高——内容是用户自己的日志和 AI 生成的总结，属于自注入。但它是标签约定的最后一个
缺口；`tagName` 机制已经就绪（第 7 轮引入），补上成本很小。

**建议**：日志内容与查询词各自包进 `<user_raw_content>` 并调用 `sanitizeUserInput`。
60 条 × 300 字的量级也应纳入
[`getRecentLogsContext`](03-P2-健壮性与体验.md) 那套字符预算考虑。
