## P0-6（回归）Room 破坏性迁移回归，且 schema 导出被关闭

**位置**：[AppDatabase.kt:16-17,37](https://github.com/Hearts-miku/PersonalSecretary/blob/2589cdd/app/src/main/java/com/example/data/local/AppDatabase.kt#L16)
**编号沿用 P0-6 以便追溯；未发布前提下按 P1 处理，发布前为阻断级**
**置信度**：高

```kotlin
version = 7,
exportSchema = false          // ← 第 4 轮曾改为 true，本轮改回
...
.fallbackToDestructiveMigration()   // ← MIGRATION_5_6 已删除
```

### 关于破坏性迁移本身

这是 [D-2](07-已修复与回归记录.md) 选项 (b) 的执行结果——删除只对开发机有意义的迁移、
重置版本号。**未发布阶段这个取舍是合理的**，不必现在撤销。

但它必须在发布前改回显式 `Migration`。首轮审计里 P0-6 的原始描述是「一次线上迭代 =
全部用户历史归零」，这个后果在发布后会原样回来。当前的
[恢复逻辑](https://github.com/Hearts-miku/PersonalSecretary/blob/2589cdd/app/src/main/java/com/example/data/repository/WorkLogRepository.kt#L50)
能从 markdown 回填日报、职业档案、工作与项目经历，但**待办和经历版本快照仍无磁盘副本**，
破坏性迁移后不可恢复。

### 关于 `exportSchema = false` —— 这一项建议现在就改回

与破坏性迁移不同，关闭 schema 导出有**累积且不可逆**的代价：

- schema 历史只能在对应版本存在的当下由 Room 生成
- 当前 v7 没有 `7.json`，将来要写 7→8 的正规迁移，只能靠手工重建 schema 定义
- 仓库里遗留的 `5.json` 与 `6.json` 已经对不上号（版本已到 7），成了孤儿文件

改回 `true` 的成本只是多提交一个 JSON 文件，却保住了将来写迁移的能力。
两件事可以分开处理：**现在恢复 `exportSchema`，发布前再撤销破坏性迁移**。

### 附带

`fallbackToDestructiveMigration()` 的无参重载在 Room 2.7 已废弃（此前代码用的是
`fallbackToDestructiveMigration(true)`），会产生 deprecation 警告。
