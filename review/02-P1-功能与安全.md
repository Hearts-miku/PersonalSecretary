## P1-15 Room 迁移从未被执行验证，且已无兜底

**位置**：[AppDatabase.kt:30-62](https://github.com/Hearts-miku/PersonalSecretary/blob/47d4f26/app/src/main/java/com/example/data/local/AppDatabase.kt#L30)
**状态**：自第 4 轮悬置至今
**置信度**：风险确实存在；迁移本身经静态比对**未发现缺陷**

第 4 轮移除了 `fallbackToDestructiveMigration`，换成手写的 `MIGRATION_5_6`——三张表
（`todo_items`、`user_career_profile`、`user_settings`）走「建新表 → 拷数据 → 删旧表 → 改名」
的完整重建。

**静态检查结论**：三条 `CREATE TABLE` 已与
[实体定义](https://github.com/Hearts-miku/PersonalSecretary/blob/47d4f26/app/src/main/java/com/example/data/local/Entities.kt)逐列比对，
列名、类型、非空、主键声明全部一致，未发现缺陷。

**风险不在代码，在于流程**：

1. `app/schemas/` 下**只有 `5.json`，没有 `6.json`**。数据库版本已是 6，
   `exportSchema = true` 且 `room.schemaLocation` 已配置到 `$projectDir/schemas`，
   构建时 Room 本应生成该文件。它不在，意味着**要么仍未实际构建，要么构建产物没提交**。
2. 移除 fallback 后，schema 校验不通过不再是「静默清库」，而是启动时抛
   `IllegalStateException` **硬崩溃**——用户只能卸载重装，数据全失。
3. 迁移只覆盖 5→6。低于 5 的库没有路径（此前是 destructive，存量库应都在 5，可接受）。

**这是当前唯一的高风险面。** 成本很低：构建一次、提交生成的 `6.json`、在一个真实的 v5
数据库上跑一遍升级即可。见 [06-修复顺序建议.md](06-修复顺序建议.md) 批次 1。

## P1-4 `CryptoManager` 仍是 Base64，不提供机密性

**位置**：[CryptoManager.kt](https://github.com/Hearts-miku/PersonalSecretary/blob/47d4f26/app/src/main/java/com/example/data/local/CryptoManager.kt)
**状态**：名实已相符，但真加密未做

第 7 轮的改动是**正确方向**：

```kotlin
/**
 * 注意：此处仅提供 Base64 编码，不提供机密性保护。
 */
object CryptoManager {
    private const val PREFIX = "v1:"
    fun encode(plainText: String): String { ... "$PREFIX$encoded" }
    fun decode(encodedText: String): String {
        if (!encodedText.startsWith(PREFIX)) return encodedText   // 存量明文原样返回
        ...
    }
}
```

方法改名为 `encode` / `decode`、加注释声明不提供机密性——**名实相符了**，不会再误导后续
维护者以为凭据已加密。`v1:` 前缀也正确解决了 [N-5](07-已修复与回归记录.md)（存量明文被
误解码损坏）。

**但首轮 P1-4 的原始诉求仍未满足**：防止本地取证 / root 场景下的凭据泄露。Base64 是编码，
任何拿到数据库文件的人一步就能还原 API Key。

次要的一点：类名仍叫 `CryptoManager`，与「不提供机密性」的注释略有张力。

**建议**：改用 `EncryptedSharedPreferences`，或 Android Keystore + AES/GCM。`v1:` 前缀机制
可以直接复用——真加密时换成 `v2:` 即可，存量 `v1:` 数据仍能正确读出。

**附带风险**：`apiKeyText` 现在用
[`rememberSaveable`](https://github.com/Hearts-miku/PersonalSecretary/blob/47d4f26/app/src/main/java/com/example/ui/screens/SettingsScreen.kt#L48)
保存，saved instance state 的 Bundle 在进程死亡时可能落盘，明文 Key 因此多了一个暴露面。
考虑只对非敏感字段用 saveable。

## 🆕 P1-16 语义搜索把用户数据裸拼进 prompt

**位置**：[GeminiRepository.kt:531-547](https://github.com/Hearts-miku/PersonalSecretary/blob/47d4f26/app/src/main/java/com/example/data/ai/GeminiRepository.kt#L531)
**置信度**：高（写法确定）／ 风险等级：中低

```kotlin
val logsPrepared = logs
    .filter { ... }.take(60)
    .map { log -> "【日期: ${log.date}】: $preview" }   // ← 未 sanitize
    .joinToString("\n\n")

val cleanQuery = AISafetyManager.sanitizeUserInput(query)

val prompt = """
    【搜索查询词/意图】: "$cleanQuery"          // ← 只加了引号，未包标签
    【候选工作记录列表】:
    $logsPrepared                              // ← 裸拼
"""
```

八个 AI 功能里，这是**唯一一个把用户数据裸拼进 prompt 的**：

- `logsPrepared` 完全没过 `sanitizeUserInput`，也不在任何标签内
- `cleanQuery` 虽然过了消毒，但因为不在标签内，转义 `<user_raw_content>` 对它没有意义

风险等级不高——内容是用户自己的日志和 AI 生成的总结，属于自注入。但它是标签约定的最后
一个缺口。第 6/7 轮刚把 `imported_data` 收进 `tagName` 机制，顺手把这处统一了成本很低。

**建议**：日志内容与查询词各自包进 `<user_raw_content>` 并调用 `sanitizeUserInput`。
注意 60 条 × 300 字的量级也应纳入 [P1-6](07-已修复与回归记录.md) 那套字符预算考虑。
